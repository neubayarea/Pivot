01 · 赛道分析

评委到底想看什么

主办方在描述里反复出现的词是 explainable（可解释）、narratives（叙事）、personalized（个性化），面向的人群点名了四类：球迷、制作方（studios）、转播方、流媒体平台。数据硬约束是只能用合成但贴近真实的足球数据，主办方不分发任何英超真实比赛数据。

450 个项目里，最常见的做法大概率是“一个能聊比赛的聊天机器人”。想脱颖而出，要在三个地方和这类项目拉开差距：AI 的每一句结论都能追溯到具体事件；多个 Agent 各有分工，而不是一个大 prompt；产品对准一个具体角色的具体工作流。

评审标准拆解

标准怎么拿分
技术实现 20%代码结构清晰、有文档；真正用上“hero 技术”（Foundry、Agent Framework、Azure）
Agentic 设计 20%多 Agent 分工、共享状态、交接、失败恢复；有新意
真实影响 20%解决的问题够重要；能上生产；对开发者、企业或终端用户有价值
UX 与呈现 20%界面直观；2 分钟视频讲清价值；前后端都有分量
赛道契合 20%紧扣“合成事件 → 可解释的比赛情报”

奖项与对应打法

  • 大奖 1st / 2nd 完整度 + 可解释性 + 多人群个性化。一等奖每人约 $4,000 现金，另有英超球赛门票和官方商店代金券
  • Best Foundry 模型目录、Prompt Flow、评测（evaluations）、追踪全部走 Foundry
  • Best Enterprise 人工审核、审计日志、内容安全、权限，能直接卖给俱乐部或媒体
  • Best Multi-Agent Agent Framework / A2A，角色清晰，有交接和失败恢复
  • Best Azure Cloud Native 事件驱动：Event Hubs → Functions / Container Apps → Cosmos DB，自动扩缩

专项奖每人约 $1,500。规则里没写一个项目能不能同时拿大奖和专项奖，最好去 Hackathon Rules 里确认。

获胜公式

  • 证据链：每条洞察挂上事件 ID，点开能看到是哪几次传球、哪次抢断支撑了这个结论
  • 确定性计算交给代码，叙事交给 LLM：控球率、压迫强度、势头曲线用 Python 算，LLM 只负责解释和改写，这样能压住幻觉
  • 一个角色，一条工作流，一个惊艳瞬间：Demo 前 15 秒就要让人看到“哇”的地方
  • 合成数据生成器本身也是亮点：可复现的比赛模拟器能当测试夹具，体现工程素养

风险与雷区

  • 时间 只剩 6 天，范围必须砍到一个核心闭环
  • 版权 视频里不能出现第三方商标或受版权保护的音乐；球队和球员全部用虚构名字
  • 数据 先看 Challenge 页面有没有给官方合成数据集或 schema；没有就自己写生成器
  • 博彩 避开投注和赔率方向，和英超的品牌调性冲突
  • 仓库 GitHub 仓库必须公开，记得删掉密钥

05 · 推荐

选哪个，怎么在 6 天内做完

首选：③ Recap Studio，借用 ② 的事实核查 Agent

理由有三点。第一，它直接对应赛题点名的“自动集锦”和“studios / 流媒体”，赛道契合没有争议。第二，审核看板、审计日志、内容安全让它天然具备企业级可信度，大奖和 Enterprise 奖可以一起冲。第三，工作流是线性的，6 天里风险最小。

如果团队前端较强、想要更强的情感冲击，⑤ Every Fan 是第二选择，差异化最明显。

06 · 组合方案

④ + ⑥ + ⑧ Pivot · 支点

一句话：实时发现比赛转折点，解释它为什么发生，再推演“如果当时不是这样”。三个选项正好构成一条闭环：⑧ 负责实时感知，④ 负责解释，⑥ 负责推演。

为什么这三个能合

  • 模拟器复用：合成数据生成器本来就要写。只要它能“从任意比赛状态继续往下模拟”，⑥ 的反事实推演几乎是顺带完成的。整个组合靠这一点成立。
  • 转折点是公共接口：④ 找出的转折点就是 ⑥ 的推演入口，也是 ⑧ 推送给平台的高光。
  • 每个模块补另一个的短板：⑧ 单独做 UX 弱，④ 单独做 Agentic 弱，⑥ 单独做可信度弱。合在一起，评审五项都有抓手。
  • 故事完整：Detect → Explain → Simulate，2 分钟 Demo 有起承转合。

代价

  • 范围 6 天可行性只有 2 分，是所有方案里最低的
  • 集成 三个子系统的接口要第一天就定死，否则联调会吃掉两天
  • 可信度 推演结果必须标明“基于合成模拟”，不能包装成预测
  • 人力 至少 3 人：后端流水线、Agent 与模拟器、前端各一人；1 到 2 人不建议做

模拟器是同一份代码，用了两次：一次生成“现实”比赛流，一次从转折点开始重跑 N 次。Agent 统一用 Microsoft Agent Framework 编排，模型和评测走 Foundry。

范围取舍（MoSCoW）

  • Must 可从任意状态续跑的模拟器；事件流 + 势头曲线；转折点检测和证据链解释；一个 what-if 场景（取消红牌或提前换人）；核查 Agent
  • Should 自然语言输入场景；Container Apps Jobs 并行扩缩；分享卡片
  • Could 压迫热区；对外 Webhook 和 API
  • Won't 手机推送、API Management、复盘报告导出、多场比赛管理

2 分钟 Demo 脚本

  • 0:00–0:20 模拟比赛实时流入，势头曲线在跳动
  • 0:20–0:50 第 63 分钟自动标出转折点，球场回放 8 个事件，旁边是带证据的三句解释
  • 0:50–1:25 输入“如果 63 分钟没换人？”，500 次模拟并行展开，胜率分布从 34% 变到 52%
  • 1:25–1:45 核查 Agent 拦下一个错误数字并打回重写
  • 1:45–2:00 架构图 + 端到端延迟看板，收尾

6 天计划（3 人并行）

  1. 10/21 周二定事件 schema 和“比赛状态”结构，三条线的接口今天定死；模拟器能跑完一整场
  2. 10/22 周三A：Event Hubs → Functions 指标。B：模拟器支持从状态续跑。C：球场组件和势头曲线
  3. 10/23 周四A：Cosmos DB + SignalR。B：转折点侦测和解释 Agent。C：接实时数据
  4. 10/24 周五what-if 闭环跑通，先在进程内跑 N 次；核查 Agent 接入。这天结束时闭环没跑通，就砍掉 ⑥，退回 ④+⑧
  5. 10/25 周六并行模拟上 Container Apps Jobs；部署；Foundry 评测；README 和架构图
  6. 10/26 周日录 Demo，写 Pitch，提交
  7. 10/27 周一缓冲

和 ③ 怎么选：这个组合的天花板更高，技术和 Agentic 分能拿满，Demo 也更有记忆点，适合冲一等奖和 Multi-Agent 奖。③ 的下限更稳，适合人少或想确保交付的队伍。判断标准很简单：有 3 个人，并且至少一人熟悉 Azure 事件驱动架构，就选组合；否则选 ③。
