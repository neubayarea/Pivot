Pivot

支点 · The Turning Point Engine for Football · Find the moment. Know why. Ask what if.

实时发现比赛的转折点，用证据解释它为什么发生，再推演“如果当时不是这样”会怎样；同一份情报按观众是谁，给出不一样的内容。本文档是四人团队在 6 天内交付黑客松作品的唯一需求依据。

01执行摘要

问题

比赛的结果常常由几个关键时刻决定，但分析师要在海量事件里手动找这些时刻，转播和流媒体平台靠人工打点，球迷争论“假如”时只能凭感觉。现有工具能告诉你发生了什么，却很少解释为什么，也没有人能回答“如果当时不是这样”。

方案

一个由多个 Agent 协作的事件驱动系统。它摄入合成比赛事件流，实时计算势头指标并检测转折点，用可追溯到事件 ID 的证据解释原因；用户可以对任意转折点提出“假如”，系统从那一刻重跑数百次模拟，给出结果分布和解释。所有输出都按观众个性化：分析师和普通球迷看到两种不同的写法，也可以按主队、关注球员和语言定制。

核心价值

  • 分析师：复盘定位转折点从几十分钟缩到几秒
  • 平台：自动产出带解释的高光事件流
  • 球迷：有依据、可分享的“假如”推演
  • 普通球迷：用自己的语言，跟着自己的球队和球员看懂比赛

成功标准（黑客松）

  • 10/26 前完成全部提交物
  • Demo 中三段闭环一次跑通，无剪辑拼接
  • Demo 中现场切换观看模式和语言，同一转折点给出两种写法
  • 植入转折点检出率 ≥ 80%
  • 解释中的数字 100% 经过核查

资源

  • 4 人 × 6 天
  • Azure 订阅 + Foundry 项目
  • 云资源预算目标 < $50（按需开启，提交后关闭）

差异化在哪里

2.3 为什么是现在

  • 英超的核心技术设施正在迁往 Azure，官方 AI 助手已经上线，联赛需要更深的实时比赛情报能力
  • 大模型已经能稳定地把结构化数据改写成自然语言，但需要确定性计算和核查来压住幻觉，这正是多 Agent 架构的用武之地
  • 云原生的事件流和弹性计算让“每个转折点跑几百次模拟”变得便宜且快
  • 赛题要求使用合成数据，反而让我们拥有标准答案：转折点是我们自己植入的，可以客观评测检出率

03方案概述

3.1 三段闭环 + 个性化

Detect

实时发现

模拟比赛事件流进入 Event Hubs，Functions 逐分钟计算势头和压迫指标，转折点侦测 Agent 判断是否出现转折。

Explain

证据解释

解释 Agent 读取转折点前后的事件窗口，写出三句解释，每句都挂事件 ID；核查 Agent 逐个核对数字。

Simulate

反事实推演

用户输入“假如”，场景翻译 Agent 把它变成参数修改；模拟器从该时刻重跑 N 次；对比分析 Agent 解释差异。

Personalize

个性化：按不同的人，给出不一样的内容

个性化不是第四个环节，而是贯穿三段的一层：转折点解释、推演结果和赛后 Recap 上屏之前，都按观众的设置改写一遍。

  • 观看模式：Analyst 模式给数字和战术术语；Casual Fan 模式讲成通俗的故事。两者是真正不同的内容，不只是换个皮肤
  • 主队与关注球员：从所选球队的视角叙述；关注球员参与的事件在球场图上高亮，卡片显示他的个人数据
  • 语言：英文、中文、西班牙文三选一

改的只是表达和视角，证据事件和数字不变。数字都在结构化的 claims 里，所以无论哪种模式、哪种语言，核查 Agent 都照样核对。偏好直接在页面上选，不需要账号。

3.2 用户旅程（分析师）

  1. 打开实时看板，选择一场正在模拟的比赛，看到比分、时间和跳动的势头曲线
  2. 第 63 分钟，曲线出现陡降，时间轴上自动出现一个转折点标记，侧栏弹出一张卡片
  3. 点开卡片：球场图回放转折点前后的 8 个关键事件，旁边是三句带证据标签的解释
  4. 点一个证据标签，对应事件在球场上高亮，并显示原始事件数据
  5. 点“假如…”，输入“如果 63 分钟没换人”，系统确认解析结果后开始推演
  6. 约 20 秒后，看到原始结果与反事实结果的胜平负分布对比、置信区间，以及一段解释
  7. 导出分享卡片，或复制该转折点的 API 链接给转播同事

3.3 差异化

证据优先每句解释都能点开看到支撑它的事件，评委可以当场验证。
计算与生成分离所有数字由代码算出，LLM 只负责选择、组织和表达，核查 Agent 兜底。
不确定性可见推演结果给出分布和置信区间，明确标注“基于合成模拟”，不包装成预测。
自带标准答案模拟器可以植入已知转折点，用来客观评测检测效果，这是使用真实数据做不到的。

3.4 范围

In scope

  • 单场比赛的实时模拟与回放（可调速 1×–20×）
  • 势头、压迫两个核心指标
  • 转折点检测、解释与核查
  • 三类“假如”场景：取消或增加红牌、提前或推迟换人、取消进球
  • 推演结果分布、置信区间与解释
  • Agent 调用轨迹面板（给评委看协作过程）
  • 只读 REST API：查询转折点
  • 观看模式：Analyst / Casual Fan
  • 选择主队和关注球员
  • 多语言输出：英文、中文、西班牙文
  • 叠加层输出：带比赛时钟的固定 JSON + 预览页
  • 终场自动生成 Match Recap（P1）

Out of scope

  • 真实比赛数据、真实球队和球员名字
  • 用户账号体系（Demo 使用单一访客身份；个性化偏好直接在页面上选，存在浏览器本地）
  • 手机推送、API Management、Webhook 订阅
  • 多场比赛管理、赛季级分析
  • 视频素材、复盘报告导出
  • 投注、赔率相关的任何功能

3.5 MVP 定义与验证假设

假设验证方式通过标准
H1 基于势头的变点检测能找到有意义的转折点20 场植入转折点的模拟比赛检出率 ≥ 80%，每场误报 ≤ 2 个
H2 计算与生成分离能消除数字幻觉核查 Agent 日志 + 人工抽查 30 条解释上屏解释的数字错误为 0
H3 从状态续跑的模拟能产生可解释的差异“取消红牌”场景对比胜率变化方向符合足球常识，且差异显著（置信区间不重叠）
H4 三段闭环能在 2 分钟内讲清队内外 3 人看 Demo 后复述3 人都能说出产品做了哪三件事

MVP 的“能用”定义：在部署好的公网地址上，任何人可以开一场模拟比赛，看到至少一个转折点及其解释，并对它发起一次推演，全程无需人工干预。

04用户故事与需求

4.1 用户故事

US-01 · Detect

作为分析师，我想在比赛进行中看到势头曲线实时更新，以便感知比赛走向。

  • 曲线按比赛分钟更新，延迟 ≤ 2 秒
  • 主客队用两种颜色区分，悬停显示该分钟数值
  • 支持 1×、5×、20× 回放速度
US-02 · Detect

作为分析师，我想让系统自动标出转折点，以便不用自己在曲线里找。

  • 转折点在时间轴上以标记出现，并带严重程度
  • 每场最多显示 5 个，按显著性排序
  • 可以点“这不是转折点”提交反馈
US-03 · Explain

作为分析师，我想看到转折点的解释和支撑证据，以便向教练说明。

  • 解释不超过 3 句，每句至少 1 个证据标签
  • 点证据标签，球场上高亮对应事件
  • 所有数字都显示“已核查”状态
US-04 · Explain

作为分析师，我想在球场图上回放转折点前后的事件，以便看清战术变化。

  • 回放窗口为转折点前 5 分钟到后 3 分钟
  • 传球、射门、抢断用不同图形
  • 可暂停、拖动
US-05 · Simulate

作为铁杆球迷，我想用一句话提出“假如”，以便验证我的观点。

  • 支持中英文自然语言输入
  • 系统先展示解析出的参数修改，确认后才开始推演
  • 无法解析时给出 3 个可选示例
US-06 · Simulate

作为铁杆球迷，我想看到推演结果的分布而不是一个数字，以便知道结论有多可靠。

  • 展示原始与反事实的胜平负分布
  • 标出 95% 置信区间和模拟次数
  • 明确标注“基于合成模拟，不是预测”
US-07 · 平台

作为OTT 工程师，我想通过 API 拿到转折点和解释，以便接入自己的系统。

  • GET /matches/{id}/turning-points 返回 JSON
  • 每条包含时间、严重程度、解释、证据事件 ID
  • 有 OpenAPI 文档
US-08 · 评委

作为评委，我想看到 Agent 是怎么协作的，以便评估 Agentic 设计。

  • 轨迹面板按时间显示每个 Agent 的输入、输出、耗时
  • 核查失败与重写在面板上清晰可见
  • 可以按转折点筛选
US-09 · Personalize

作为普通球迷，我想用通俗的话看懂转折点，以便不被术语和数字劝退。

  • 一键切换 Analyst / Casual Fan，同一转折点马上换一种写法

6.3 模拟器设计

模拟器是整个系统的地基，同时服务三件事：生成“现实”比赛、从任意状态续跑推演、植入已知转折点做评测。采用控球链马尔可夫模型，复杂度够低，6 天内可以写完并调好。

状态（MatchState）

  • 比赛时钟（秒）、比分
  • 控球方、球所在区域（12 × 8 网格）
  • 双方在场人数、每名球员体能值
  • 双方战术参数：进攻倾向、压迫强度、阵型宽度
  • 随机数生成器状态（保证可复现）

转移规则

  • 每一步按区域和战术参数抽样动作：传球、带球、射门、丢失球权
  • 成功率 = 基础率 × 球队实力 × 体能 × 人数修正
  • 射门转化率取决于射门区域的威胁值（类 xT 网格）
  • 红牌：人数修正降为约 0.85，压迫强度下降
  • 换人：新球员体能重置，可改变战术参数
标定：用 200 场模拟比赛检查统计量是否“像足球”：场均进球约 2.5 到 3、射门约 20 到 28、控球率分布合理。不像就调基础率，D1 结束前完成。

6.4 指标与转折点算法

名称定义实现
威胁值 threat每个事件让球队进球概率增加的估计，按起止区域查威胁网格网格由模拟器离线统计得到
势头 momentum主队威胁值减客队威胁值，按分钟汇总后做指数加权平均（半衰期 5 分钟）取值约在 −1 到 1
压迫 pressure每分钟在对方前三分之一区域的抢断、拦截、施压次数按队分别计算
候选转折点对势头序列做 CUSUM 变点检测；变化幅度超过阈值并持续 ≥ 5 分钟阈值用评测集调参
转折点判定侦测 Agent 结合候选点前后的关键事件（进球、红牌、换人、战术变化），判断是否成立并给出严重程度 1–3mini 模型，结构化输出

6.8 推演的统计方法

  • 原始组与反事实组各跑 N 次（默认 500），都从同一状态快照出发，只在场景参数上不同
  • 两组使用相同的种子序列（公共随机数），降低方差，让差异更多来自场景本身
  • 胜平负比例的 95% 置信区间用 Wilson 区间计算
  • 界面上只在置信区间不重叠时使用“显著提高或降低”这类措辞，否则显示“差异不明显”，这条规则也由核查 Agent 执行

Demo 脚本（120 秒）

0–15″一句话痛点：“比赛由几个瞬间决定，但没人告诉你是哪几个，更没人告诉你假如。”
15–35″模拟比赛实时流入，势头曲线跳动；第 63 分钟自动标出转折点
35–55″球场回放 + 三句解释（Analyst 模式）；点证据标签，事件高亮
55–70″切到 Casual Fan 模式、选主队和关注球员：同一个转折点换成球迷能懂的说法；再一键切成中文
70–95″输入“如果 63 分钟没换人？”，500 次模拟展开，分布变化
95–108″轨迹面板：核查 Agent 拦下错误数字，解释 Agent 重写
108–120″叠加层预览 + 架构图；结尾口号

11赛后路线

这一节用于 Pitch 的“真实影响”部分，说明产品不止是 Demo。

阶段目标客户形态商业模式假设
1 · 平台 API转播方、OTT 平台接入授权数据源后提供转折点与解释 API按比赛场次或调用量计费
2 · 分析师工作台俱乐部、青训学院、战术内容创作者SaaS，加入多场对比与报告导出按席位订阅
3 · 球迷互动转播方和平台的 C 端产品白标 What-If 组件，嵌入 App 与直播间与平台分成或授权费

以上为假设，没有做市场规模测算；真实落地需要接入授权的比赛数据。
