GitHub + Asana 怎么分工

我理解你说的“as 啥的”是 Asana。如果指的是 Azure Boards，分法一样。

  • GitHub 管“怎么做”：所有任务都是 issue，代码、PR、CI 都挂在上面。任务状态只看 GitHub。
  • Asana 管“什么时候交”：6 个里程碑和 6 个全员事项（开工会、两次集成检查、录视频、提交）。已经导出成 docs/plan/asana-schedule.csv，在 Asana 里用 CSV 导入就行。
  • 不重复记录：同一件事只在一边出现。Asana 的里程碑描述里贴上对应的 GitHub milestone 链接。

说实话，3 天的冲刺用一个工具最省事：GitHub Projects 自带时间线视图，也能放日程。Asana 是可选项，喜欢看日历视图再加。

看板怎么设

  • 列：Backlog → Ready（依赖已完成）→ In progress → In review → Done
  • 字段：负责线（A/B/C/D）、里程碑（M0 到 M5）、预估小时、优先级
  • 视图：按状态的看板；按负责人的表格；按里程碑的时间线
  • 在制品上限：每人同时最多 2 张卡在 In progress
  • 标签：must should could team area:* blocked contract demo-critical bug
  • 自动化：PR 合并后，关联的 issue 自动关闭并移到 Done

分支、提交、PR

  • 分支名：b/B03-simulator-core（线 / 任务 ID / 简述）
  • 提交信息：B03: add possession-chain step
  • 不直接推 main；一个 PR 只做一个任务，尽量少于 400 行，当天合并
  • PR 模板已经放在 .github/：关联任务、验证方式、契约勾选
  • 统一用 Squash 合并，main 的历史一个任务一行

Review 与 CI

  • A 和 B 互审；D 的 Python 由 A 审；C 的前端由 D 审交互和文案；D 的前端由 C 审
  • 收到 Review 请求后 30 分钟内响应；看不完就先回一句“晚点看”
  • CI 检查四项：代码风格、单测、契约导出是否同步、密钥扫描
  • 私有仓库的分支保护需要付费计划，所以先靠约定执行；转公开后立刻打开保护

契约变更

  • 领域模型由 B 负责，是前后端共用的唯一来源
  • M0 之后只允许新增可选字段
  • 改动契约的 PR 标题加 [contract]，在群里 @ 全员
  • 生成的 JSON Schema 和 TS 类型要一并提交，CI 会检查有没有漏

完成定义

  • 符合冻结的契约
  • 确定性逻辑（模拟器、指标、核查）有单元测试
  • 在本地形态下跑通，部署后冒烟测试通过
  • 对应的 Demo 步骤可以现场演示
  • 在轨迹和遥测里能看到这项功能的记录

这些约定也写进了仓库根目录的 CONTRIBUTING.md，新人只看那一个文件就够了。

站会每人三句话

  1. 上次站会以来合并了什么（报 PR 编号）
  2. 下次站会前要合并什么
  3. 被什么卡住、需要谁帮忙

卡住了怎么办

  • 卡住 45 分钟：在群里 @ 相关的人
  • 卡住 2 小时：issue 加 blocked，到站会上重新排
  • 里程碑亮红灯：按下面的顺序砍需求
