# ADR-0002：比赛事件流使用 Azure Event Hubs

- 状态：已采纳（属于 C2 形态；C1 形态下由进程内 `EventSink` 代替）
- 日期：2026-10-23
- 相关：ADR-0001、ADR-0011

## 背景

模拟器按比赛时钟产出事件，每场约 1,600 条；60 倍速回放时约每秒 18 条。下游的指标计算要求同一场比赛的事件严格有序，能够重放，并且以后可以接更多消费者（例如调试旁路、归档）。事件驱动架构本身也是 Best Azure Cloud Native 奖的核心评审点。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Event Hubs** | 分区内有序（分区键为 matchId）；保留期内可重放；与 Functions 原生集成；吞吐高 | 多一个资源；投递语义是“至少一次” |
| B. Service Bus 主题 + 会话 | 用会话可保证有序，支持逐条确认 | 不能重放；它是消息代理而不是日志，不适合高频遥测 |
| C. 模拟器直接 HTTP 调用指标服务 | 最简单 | 强耦合；没有缓冲；下游一抖动上游就阻塞 |
| D. 在 AKS 上自建 Kafka | 生态成熟 | 运维成本远超黑客松预算 |

## 决策

采用 Event Hubs Standard，1 个吞吐量单位。

- 一个事件中心 `match-events`，2 个分区，分区键为 `matchId`。
- 消费者组：`$Default` 给 Functions；另留 `debug` 供旁路调试。Basic 层只允许一个消费者组，所以选 Standard。
- 每条事件带 `schema_version`、`seq`（同一场比赛内单调递增）和 W3C `traceparent`。

## 后果

- **正面**：生产和消费解耦；需要时可以按 `seq` 重放；为接入新消费者留了余地。
- **负面**：至少一次投递，消费者必须幂等。按“分钟文档”加 `seq` 去重做 upsert。
- **风险**：引入后端到端延迟会增加约 100 到 500 毫秒，仍在 2 秒预算内。C2 没能按时就绪时，退回 C1 的进程内 `EventSink`，业务代码不受影响。
