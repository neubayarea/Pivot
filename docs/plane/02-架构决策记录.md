## ADR-0001：模块化单仓 + 端口与适配器 + 三档部署形态

- 状态：已采纳
- 日期：2026-10-23
- 决策者：A（平台）· B（模拟）· C（体验）· D（Agent）
- 相关：ADR-0002、ADR-0003、ADR-0009、ADR-0011

## 背景

距离提交只剩 3.5 天，4 个人需要从第一天起并行开发。目标架构要用到十余个 Azure 服务，这些服务又是 Cloud Native 奖的看点。如果业务代码直接调用每个服务的 SDK，任何一个服务没开通或者没调通，整条链路都会卡住，联调也会把剩下的时间吃光。演示的可靠性必须排在架构的完整度之前。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 微服务优先：每个能力单独一个服务，直接调用 Azure SDK | 部署层面解耦彻底 | 脚手架和联调成本最高；本地跑不通整条链路；一个服务出问题就阻塞所有人 |
| B. 单体脚本：一个 Python 进程做完所有事 | 第一天就能跑 | 展示不了云原生；Agent 角色边界模糊；四个人改同一批文件，冲突多 |
| **C. 模块化单仓 + 端口与适配器** | 领域核心不依赖任何云服务；外部能力都通过端口接入；本地和云端走同一份业务代码 | 多一层适配器（约占代码量 10%）；端口要刻意保持精简 |

## 决策

采用方案 C。

- **领域核心** `packages/pivot_core` 只依赖 `pydantic` 和 `numpy`，里面包含领域模型、模拟器、指标与变点算法、统计函数，以及端口接口。
- **端口**：`EventSink`、`WorkQueue`、`MatchRepository`、`TraceRepository`、`LivePublisher`、`ModelClient`、`SimulationExecutor`。
- **适配器** `packages/pivot_adapters`：`local/`（内存总线、SQLite 或内存存储、FastAPI WebSocket、桩模型）和 `azure/`（Event Hubs、Service Bus、Cosmos DB、Web PubSub、Foundry、Container Apps Jobs）。
- **同一个 Python 镜像，三个入口**：`api`、`simulator`、`worker`。
- **部署形态**用环境变量 `PIVOT_PROFILE` 切换：

| 形态 | 组成 | 用途 |
|---|---|---|
| L（本地） | 单进程，内存适配器；模型调用走 Foundry 或桩 | 开发、单元测试；演示的最后兜底 |
| C1（云端最小） | 在 Container Apps 上运行 api / simulator / worker，配合 Service Bus、Cosmos DB、Web PubSub、Foundry；指标在模拟器进程内计算 | 必须交付的形态 |
| C2（云端完整） | 在 C1 基础上加 Event Hubs + Functions 计算指标，以及 Container Apps Jobs 分片推演 | 应交付，冲 Cloud Native 奖 |

- **契约优先**：`pivot_core.domain` 里的 Pydantic 模型是唯一事实来源，由它导出 JSON Schema，再生成前端的 TypeScript 类型。

## 后果

- **正面**：第一天就能用假数据并行开发；砍需求只改部署形态，不改代码结构；演示时 C2 出问题可以退回 C1，C1 出问题可以退回 L。
- **负面**：适配器带来额外代码；新加一个外部能力必须先定义端口。
- **风险与缓解**：本地适配器和 Azure 适配器的行为可能不一致。缓解办法是给每个端口写一组契约测试，CI 里跑本地实现，部署后对云端跑一次冒烟测试。

## ADR-0002：比赛事件流使用 Azure Event Hubs

- 状态：已采纳（属于 C2 形态；C1 形态下由进程内 `EventSink` 代替）
- 日期：2026-10-23
- 相关：ADR-0001、ADR-0011

## 背景

模拟器按比赛时钟产出事件，每场约 1,600 条；60 倍速回放时约每秒 18 条。下游的指标计算要求同一场比赛的事件严格有序，能够重放，并且以后可以接更多消费者（例如调试旁路、归档）。事件驱动架构本身也是 Best Azure Cloud Native 奖的核心评审点。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Event Hubs** | 分区内有序（分区键为 matchId）；保留期内可重放；与 Functions 原生集成；吞吐高 | 多一个资源；投递语义是“至少一次” |
| B. Service Bus 主题 + 会话 | 用会话可保证有序，支持逐条确认 | 不能重放；它是消息代理而不是日志，不适合高频遥测 |
| C. 模拟器直接 HTTP 调用指标服务 | 最简单 | 强耦合；没有缓冲；下游一抖动上游就阻塞 |
| D. 在 AKS 上自建 Kafka | 生态成熟 | 运维成本远超黑客松预算 |

## 决策

采用 Event Hubs Standard，1 个吞吐量单位。

- 一个事件中心 `match-events`，2 个分区，分区键为 `matchId`。
- 消费者组：`$Default` 给 Functions；另留 `debug` 供旁路调试。Basic 层只允许一个消费者组，所以选 Standard。
- 每条事件带 `schema_version`、`seq`（同一场比赛内单调递增）和 W3C `traceparent`。

## 后果

- **正面**：生产和消费解耦；需要时可以按 `seq` 重放；为接入新消费者留了余地。
- **负面**：至少一次投递，消费者必须幂等。按“分钟文档”加 `seq` 去重做 upsert。
- **风险**：引入后端到端延迟会增加约 100 到 500 毫秒，仍在 2 秒预算内。C2 没能按时就绪时，退回 C1 的进程内 `EventSink`，业务代码不受影响。

## ADR-0003：Agent 任务使用 Azure Service Bus 队列

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0004、ADR-0009

## 背景

“转折点候选”和“推演运行”都是离散任务，每个任务的 Agent 链要跑 5 到 15 秒。这类任务需要可靠处理：Worker 崩溃后任务不能丢，失败要能重试，坏消息要有地方隔离。它们还要和发起方（指标处理、API）异步解耦，Worker 要能按队列长度扩缩。Multi-Agent 奖明确考察“从失败中恢复”的能力。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Service Bus 队列** | 窥视锁定；自动重试；死信队列；重复检测；KEDA 可按队列扩缩 | Standard 层有基础费用 |
| B. Storage 队列 | 最便宜、最简单 | 没有原生死信和重复检测；消息最大 64 KB |
| C. Event Grid | 推送模型，延迟低 | 适合通知，不适合需要确认和重试的工作队列 |
| D. 复用 Event Hubs | 少一个资源 | 日志模型，不能逐条确认，失败重试很难做 |

## 决策

采用 Service Bus Standard（需要重复检测，Basic 层不支持）。

| 队列 | 最大投递次数 | 锁定时长 | 重复检测窗口 | 消息 ID |
|---|---|---|---|---|
| `pivot-candidates` | 5 | 60 秒（自动续期） | 10 分钟 | `{matchId}:{minute}` |
| `scenario-runs` | 3 | 120 秒（自动续期） | 10 分钟 | `scenarioId` |

Worker 使用 KEDA 的 Service Bus 扩缩器：演示期间最少 1 个副本，避免冷启动；最多 5 个。

## 后果

- **正面**：Worker 崩溃后消息自动重投；毒消息进入死信队列并触发告警；重复检测加上确定性 ID，保证同一候选不会生成两个转折点。
- **负面**：Agent 链可能超过锁定时长，必须实现锁续期。
- **风险**：如果某个候选在死信队列里卡住，前端看到的转折点会一直停在“待确认”。缓解办法是在比赛状态里给“待确认”设 60 秒超时，超时后转为“降级”。

## ADR-0004：Agent 编排使用 Microsoft Agent Framework 显式工作流，循环有上限

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0005、ADR-0003

## 背景

评审中 Agentic 设计占 20%。Multi-Agent 奖考察四点：每个 Agent 角色清晰，通过共享状态协作，交接有效，能从失败中恢复。与此同时，解释必须在 10 秒内上屏，数字必须 100% 正确。主办方点名的 hero 技术包括 Microsoft Agent Framework 和 Foundry。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 单个大 prompt | 实现最快 | 没有角色边界；不能只重试某一步；很难单独评测 |
| B. 自由对话式多 Agent（由 LLM 决定下一位发言者） | 看起来“自主” | 路径不可预测；延迟和成本失控；无法复现 |
| **C. Agent Framework 显式工作流（图）** | 节点和边是固定的；条件边可以表达“核查失败就回去重写”；每个节点可单独测试；自带可观测性 | 灵活度不如方案 B；SDK 还在快速演进 |
| D. LangGraph 等第三方编排 | 能力相近 | 不是主办方的 hero 技术 |
| E. Foundry Agent Service 托管 Agent | 托管线程，门户里可直接看到 | 函数工具需要往返调用，延迟更高；对确定性工具的控制弱 |

## 决策

采用方案 C，模型来自 Foundry 的部署。

- **发现链**：Judge（判定）→ Explainer（解释）→ Verifier（核查）。核查不通过就沿条件边回到 Explainer，最多 2 次，之后走 TemplateExplainer（确定性模板）。
- **推演链**：Translator（场景翻译，只在自然语言输入时调用）→ 执行器（确定性）→ Comparator（对比）→ Verifier。
- **共享状态**：工作流上下文保存在 Cosmos DB 的比赛分区里，每个节点在交接时写一条 `AgentTrace`。
- **工具**：全部是确定性 Python 函数（`get_events`、`get_metrics`、`compute_stat`、`list_scenario_types`、`get_sim_summary`）。
- **SDK 隔离**：用我们自己的 `AgentRuntime` 端口包住 Agent Framework，并锁定 SDK 版本，防止上游接口变化扩散到业务代码。
- **扩展**（P2）：把“解释某个转折点”暴露为 A2A 端点，供英超 Companion 这类球迷助手调用，正好对应我们“情报引擎”的产品定位。

## 后果

- **正面**：延迟和成本可预测；每次交接和重写都留在轨迹里，可以直接在 Demo 中展示；每个节点可以用固定输入做单元测试。
- **负面**：看不到“涌现”式的协作；新增一种 Agent 需要修改工作流图。
- **风险**：SDK 接口变动 → 版本锁定加端口隔离；模型限流（429）→ 指数退避重试 2 次，然后降级。

## ADR-0005：计算与生成分离——数字必须附统计引用，由确定性核查兜底

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0004

## 背景

体育 AI 最大的信任问题是编造数字。赛题反复强调 explainable，PRD 的目标是“上屏解释中的数字错误为 0”。这件事不能只靠 prompt 来保证。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 自由文本，再由另一个 LLM 评审 | 实现简单 | 评审 LLM 自己也会漏判；多一次调用，成本和延迟更高 |
| B. 纯模板 | 零幻觉 | 文字单调，看不出洞察，展示不出 Agent 的价值 |
| **C. 结构化输出 + 统计引用 + 确定性核查** | 数字可以复算；证据可以点开；核查失败的过程可以展示 | prompt 更复杂；要维护一份统计词表 |

## 决策

采用方案 C。

1. Explainer 和 Comparator 必须输出结构化 JSON：每句话包含 `text`、`evidence_ids[]` 和 `claims[]`。每个 claim 包含 `value`、`unit` 和 `stat_ref {metric, team, window}`。
2. `metric` 只能从统计词表中选，初版 15 项，例如 `passes_final_third`、`shots`、`xg`、`pressures`、`duels_won`、`momentum_avg`。
3. Verifier 是确定性规则，按以下顺序检查：
   - 用 `StatCalculator` 重算每个 claim，容差为：计数精确相等，百分比 ±0.5 个百分点，xG ±0.01；
   - 每个 `evidence_id` 必须存在，且落在转折点前 8 分钟到后 5 分钟的时间窗内；
   - 句子里的方向词（rose / fell 等）必须和两个时间窗的差值符号一致；
   - 只有置信区间不重叠时，才允许使用“显著”类措辞；
   - 检查句数、字数上限和禁用词（博彩用语、绝对化措辞）。
4. 核查不通过时，把具体差异作为反馈交给 Explainer 重写，最多 2 次；仍不通过就用 TemplateExplainer 降级。
5. 最终上屏的数字一律取 `StatCalculator` 的计算值，不取模型写的原文。

## 后果

- **正面**：上屏数字按设计就能复算；“核查 Agent 拦下错误数字”是 Demo 中可以直接展示的一幕；核查规则可以单元测试。
- **负面**：统计词表需要维护；prompt 中要注入词表和 few-shot 示例，会增加约 1.5k tokens。
- **风险**：首次通过率低会推高延迟。缓解办法是 few-shot 示例加 JSON Schema 约束；把首次通过率作为评测指标，目标 ≥70%。

## ADR-0006：存储使用 Cosmos DB for NoSQL（Serverless），按 matchId 分区

- 状态：已采纳
- 日期：2026-10-23

## 背景

所有访问都以“一场比赛”为边界：按分钟读取时间窗，按 ID 读取转折点和推演，追加 Agent 轨迹。60 倍速回放时写入会突然变密。团队没有时间做数据库运维和 schema 迁移，成本也要压在最低。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Cosmos DB NoSQL Serverless** | 按请求单位计费；单分区查询便宜；支持 TTL；SDK 和身份认证齐全 | 不能跨分区做分析（本次不需要） |
| B. Azure SQL 或 PostgreSQL Flexible | 关系模型，团队熟悉 | 要做 schema 迁移；有常驻费用；用不上 join |
| C. Table Storage | 极便宜 | 查询能力弱；没有 TTL 和二级索引 |
| D. Redis | 读写最快 | 不适合作为持久化主存储 |

## 决策

采用方案 A，建两个容器：

| 容器 | 分区键 | 文档类型 | TTL |
|---|---|---|---|
| `match_data` | `/matchId` | `match`、`minute`、`pivot`、`scenario`（用 `type` 字段区分） | 无 |
| `agent_traces` | `/matchId` | `trace` | 7 天 |

- **分钟文档**（`id = {matchId}:{minute}`）把这一分钟的事件、指标和整分钟时刻的状态快照放在一起。每场比赛约 90 次写入，避免 1,600 次逐条写入。快照同时用于推演续跑。
- **比赛文档**保存运行状态（EWMA、CUSUM 累加器、冷却期），用 ETag 乐观并发控制写入。

## 后果

- **正面**：几乎所有查询都是单分区；不需要迁移脚本；轨迹到期自动清理。
- **负面**：赛季级或跨比赛分析需要另外导出，不在本次范围内。
- **风险**：Serverless 层的突发请求单位有上限。缓解办法是按分钟批量写入，并开启 SDK 的 429 重试。

## ADR-0007：实时推送使用 Azure Web PubSub

- 状态：已采纳（替换 PRD 中的 SignalR Service）
- 日期：2026-10-23

## 背景

前端需要实时收到指标、转折点和推演进度，从事件产生到界面更新的 p95 不超过 2 秒。后端全部是 Python，会有多个发布方：模拟器（或指标处理函数）和 Worker。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Azure Web PubSub** | 有官方 Python 服务端 SDK；浏览器用原生 WebSocket 即可连接；支持按组推送；Serverless | 免费层的连接数和每日消息数有限 |
| B. Azure SignalR Service | 生态成熟 | 最佳搭档是 ASP.NET 或 Functions 绑定；Python 服务端只能走 REST；前端还要引入客户端库 |
| C. API 直接用 SSE 推送 | 最简单 | 长连接全压在 API 上；横向扩容需要额外的背板 |
| D. 轮询 | 零基础设施 | 延迟高，请求浪费 |

## 决策

采用 Web PubSub。

- 每场比赛一个组：`match.{matchId}`。前端调用 `GET /api/realtime/negotiate?matchId=` 拿到带“加入该组”权限的客户端连接 URL。
- 所有消息使用统一信封：`{type, matchId, seq, ts, payload}`。`type` 取值见架构文档 §7.2。
- 本地形态 L 由 FastAPI 的 WebSocket 端点实现同样的信封，前端代码不用区分环境。
- 开发期用免费层；评审期升级为 Standard 1 单位，应对多位评委同时访问。

## 后果

- **正面**：推送和 API 的扩缩互不影响；多个发布方可以直接推送，不用绕经 API。
- **负面**：多一个资源和一层身份配置。
- **风险**：断线期间会漏消息。缓解办法是客户端自动重连后，用 `GET /timeline?sinceSeq=` 补齐缺失的数据。

## ADR-0008：模拟器采用控球链马尔可夫模型 + 状态快照 + 公共随机数

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0009、ADR-0010

## 背景

赛题要求只能用合成数据。推演需要能从比赛的任意时刻接着往下跑；评测需要能把已知的转折点植入比赛；整个模拟器必须由一个人在 1.5 天内写完并完成标定。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 控球链马尔可夫模型** | 12×8 区域网格 + 动作概率 + 体能和人数修正；单场只需毫秒级；可以做快照；参数含义清楚 | 没有球员坐标级的空间数据 |
| B. 基于物理和追踪数据的 22 人模拟 | 最真实 | 工作量大，运行慢，3.5 天内做不完 |
| C. 让 LLM 生成事件 | 文本像真的 | 无法复现；慢且贵；统计特性不可控 |
| D. 回放一份固定的合成数据集 | 零开发 | 做不了反事实推演 |

## 决策

采用方案 A。

- **状态** `MatchState`：比赛时钟、比分、控球方、球所在区域、双方在场球员（含体能）、红牌、剩余换人次数、战术参数（进攻倾向、压迫等级、阵型宽度），以及 `rng_state`（numpy PCG64 生成器的状态）。
- **每一步**：按区域和战术参数抽样一个动作（传球、带球、射门、犯规），按动作类型抽样耗时，按“实力 × 体能 × 人数”修正成功率。射门的进球概率取决于区域威胁值和对方压迫。
- **快照**：每个整分钟保存一次 `MatchState`，写入分钟文档。从快照续跑的结果逐位一致。
- **公共随机数**：推演时第 i 次的基线运行和反事实运行使用同一个种子 `seed_base + i`，两组结果成对比较，方差更小。
- **植入接口**：`PlantSpec{minute, type, team, ...}` 在指定时刻强制发生某个事件，用于评测集和 Demo 预设。
- **标定**：用 200 场模拟比赛核对场均进球（2.5 到 3.0）、射门（20 到 28）和控球率分布。标定结果写进 README。

## 后果

- **正面**：单场模拟约 10 毫秒（估算），推演可以在几秒内完成；结果可复现；评测有标准答案。
- **负面**：球场图只能展示区域级位置，回放动画是“区域到区域”的移动。
- **风险**：推演结果可能被质疑“不像足球”。缓解办法是公开标定统计和局限，并在界面上始终标注“基于合成模拟，不是预测”。

## ADR-0009：推演执行器可插拔——默认本地进程池，大规模时用 Container Apps Jobs

- 状态：已采纳（Jobs 适配器属于 Could，按时间决定是否交付）
- 日期：2026-10-23
- 相关：ADR-0001、ADR-0008

## 背景

默认推演规模是基线和反事实各 500 次。单核估算约 10 秒，PRD 的要求是 30 秒内完成。Cloud Native 的叙事希望展示弹性扩展，但演示首先要稳定、要快。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 模拟器容器内的进程池（2 vCPU）** | 没有冷启动；1,000 次运行估算 3 到 6 秒 | 只能纵向扩展 |
| B. Container Apps Jobs 分片 | 可以并行跑上万次；横向弹性 | 每次作业执行有调度和镜像拉取开销（数秒到数十秒），N 较小时反而更慢 |
| C. Durable Functions 扇出扇入 | 编排能力强 | Python 冷启动加上编排复杂度；与 Jobs 的定位重叠 |
| D. Azure Batch | 适合超大规模计算 | 对本场景过重 |

## 决策

定义端口 `SimulationExecutor.run(spec, n_runs) -> SimSummary`，提供两个适配器：

- `LocalPoolExecutor`：默认实现，用于 N ≤ 2,000；
- `AcaJobExecutor`：用于 N > 2,000。把任务拆成若干分片（每片 250 次），每个分片把结果写入 Blob，Worker 汇总。

两个适配器调用同一个 `run_shard(spec, seeds)` 函数，结果逐位一致。

## 后果

- **正面**：Demo 主线（500 次）延迟最低、最稳定；架构上保留了横向扩展路径。如果有时间，可以在视频中加一段 5,000 次分片运行的展示。
- **负面**：如果 Jobs 适配器没做完，Cloud Native 的展示会少一个亮点；README 和架构图中如实说明扩展方式。
- **风险**：进程池占满 CPU 会拖慢实时比赛。缓解办法是实时比赛和批量推演分别部署成两个 Container App 修订版本（或者限制进程池最多 2 个进程）。

## ADR-0010：转折点检测采用“EWMA 势头 + CUSUM 变点初筛 + LLM 判定”

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0004、ADR-0008

## 背景

检测必须同时满足三点：实时（候选点在 5 秒内出现）、可解释（能说出为什么判定为转折点）、可评测（检出率可以量化）。如果让 LLM 逐分钟扫描事件流，延迟高、成本高，结果也不稳定。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 纯规则：进球、红牌、换人即算转折点 | 简单，零成本 | 漏掉没有关键事件的战术转折；误报多 |
| B. 纯 LLM 判定 | 理解语义 | 慢、贵、不稳定，无法量化评测 |
| **C. 统计变点初筛 + LLM 判定** | 参数可调，可评测；只在候选点调用 LLM | 参数敏感，需要用评测集调参 |
| D. 贝叶斯在线变点检测（BOCPD） | 统计上更严谨 | 实现和调参时间不够 |

## 决策

采用方案 C。

- **势头**：`m_t = tanh(α · EWMA(threat_home − threat_away))`，取值在 −1 到 1 之间，正值表示主队占优；半衰期 5 分钟；每个半场开始时重置（借鉴 Bundesliga Match Momentum）。
- **变点**：对 `m_t` 做双向 CUSUM，参数 `k`（漂移）和 `h`（阈值）。报警后累加器清零。候选点必须持续 5 分钟以上，两个转折点之间至少隔 8 分钟，每场最多 5 个。
- **严重程度**：设 `Δ` 为候选点前后各 5 分钟势头均值之差。`Δ ≥ 0.6`，或窗口内有进球或红牌时为 3 级；`Δ ≥ 0.45`，或窗口内有换人时为 2 级；其余为 1 级。
- **LLM 判定**：Judge 使用 mini 模型，输入候选点、窗口内的关键事件和指标，输出 `{is_pivot, severity, trigger_event_ids}`。
- **调参**：在 20 个带植入转折点的种子上网格搜索 `k` 和 `h`。目标是检出率 ≥80%（允许 ±3 分钟误差），每场误报 ≤2 个。

## 后果

- **正面**：每场比赛只调用 LLM 5 到 10 次；检出率可以量化，写进 README。
- **负面**：在合成数据上调出来的阈值，不一定适用于真实比赛数据（在 README 中说明）。
- **风险**：阈值过敏感会导致误报，在界面上刷屏。缓解办法是冷却期、数量上限，加上 Judge 的二次判定。

## ADR-0011：流式指标计算使用 Azure Functions（Flex Consumption，Python，Event Hubs 触发）

- 状态：已采纳（属于 C2 形态）
- 日期：2026-10-23
- 相关：ADR-0001、ADR-0002、ADR-0010

## 背景

在 C2 形态中，指标计算要由事件驱动、按分区有序处理，并能按需扩缩；同时最好和 C1 形态共用同一份分析代码。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Azure Functions，Event Hubs 触发** | 原生触发和检查点；直接复用 `pivot_core.analytics`；按分区扩缩 | 有冷启动 |
| B. Azure Stream Analytics | 类 SQL 的时间窗计算 | CUSUM 和威胁网格要写 UDF；没法复用 Python 代码 |
| C. Fabric 实时智能（Eventstream + KQL） | 实时分析能力强 | 需要容量费用；搭建时间长；对本次范围过重 |
| D. 在模拟器进程内计算 | 最快 | 失去事件驱动的解耦（这正是 C1 的做法，作为退路保留） |

## 决策

采用方案 A，Flex Consumption 计划，保持 1 个常备实例，用来消除演示时的冷启动。

- 每批事件的处理步骤：按 `seq` 去重；upsert 分钟文档；在分钟边界更新 EWMA 和 CUSUM；候选点入队到 `pivot-candidates`；通过 Web PubSub 推送 `metric.updated`。
- 每场比赛的运行状态保存在 match 文档中，用 ETag 乐观并发写入。同一场比赛只落在一个 Event Hubs 分区，因此同一时刻只有一个写入者。

## 后果

- **正面**：C1 和 C2 共用同一份分析代码；指标计算和模拟器在部署上解耦。
- **负面**：多一套部署流水线（Functions 和 Container Apps 分开发布）。
- **风险**：批处理在检查点之前失败会导致重复处理。缓解办法是全部操作都做成幂等 upsert，并按 `seq` 去重。

## ADR-0012：前端使用 React + Vite + D3，部署在 Static Web Apps

- 状态：已采纳
- 日期：2026-10-23

## 背景

评审中 UX 占 20%。界面需要三种定制图表：球场事件图、势头曲线和结果分布图。前端由 C 一个人负责，视觉风格要能随最终选定的 UI 方案切换。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. React + TypeScript + Vite + D3** | 完全可控；开发服务器快；静态托管便宜 | 图表组件要自己写 |
| B. Next.js | 框架能力全面 | 用不上服务端渲染，反而更重 |
| C. Streamlit 或 Gradio | Python 开发者上手最快 | 界面一眼就能认出来，定制和品牌化困难，UX 分吃亏 |
| D. Power BI Embedded | 企业感强 | 实时交互和定制能力弱；有授权成本 |

## 决策

采用方案 A。

- React 负责渲染 SVG，D3 只用于比例尺、路径生成和时间格式化，避免和 React 抢 DOM。
- REST 请求用 TanStack Query；实时连接用原生 WebSocket，走 Web PubSub 的 JSON 子协议。
- 类型来自 `packages/contracts` 自动生成的 TypeScript 文件，禁止手写接口类型。
- 主题完全由 CSS 变量驱动，选定 UI 风格后只需替换一份令牌文件。
- 托管在 Static Web Apps 免费层；API 地址通过构建时的环境变量注入；API 端开启 CORS 白名单。

## 后果

- **正面**：UI 风格可以按评审需要切换；同一套组件既能用于 Demo，也能用于 README 截图。
- **负面**：三个图表组件约需 1 人天。
- **风险**：D3 和 React 的状态同步问题。约束是：D3 只计算，不直接操作 DOM。

## ADR-0013：平台基线——azd + Bicep、GitHub Actions OIDC、托管身份

- 状态：已采纳
- 日期：2026-10-23

## 背景

项目要用到十余个 Azure 资源，必须能一键创建和销毁：赛后不删干净就会持续计费。仓库会公开，不能出现任何密钥。只剩 3.5 天，部署必须做到一条命令完成。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. azd + Bicep（尽量使用 Azure Verified Modules）** | `azd up` 一条命令完成创建和部署；Azure 原生；模块现成 | 团队可能对 Bicep 不熟 |
| B. Terraform | 支持多云，生态大 | 状态文件要单独管理；接入 azd 部署流程还要额外配置 |
| C. 在门户里手工创建 | 第一次最快 | 不可复现，容易出错，赛后也难清理干净 |

## 决策

- 用 azd 加 Bicep：根目录放 `azure.yaml`，`infra/` 下放 `main.bicep` 和各模块。开发环境的环境名为 `pivot-dev`，评审期的环境名为 `pivot-demo`。
- 在 GitHub Actions 中用 OIDC 联合凭据登录 Azure，不保存客户端密钥。
- 服务之间全部使用用户分配的托管身份加数据面 RBAC，不使用连接字符串：

| 服务 | 角色 |
|---|---|
| Cosmos DB | Cosmos DB Built-in Data Contributor（Cosmos 原生 RBAC） |
| Service Bus | Azure Service Bus Data Sender / Data Receiver |
| Event Hubs | Azure Event Hubs Data Sender / Data Receiver |
| Web PubSub | Web PubSub Service Owner |
| Foundry 模型 | Cognitive Services OpenAI User（以 Foundry 当前的角色要求为准） |
| Container Registry | AcrPull |
| Storage | Storage Blob Data Contributor（Functions 宿主存储和推演分片结果） |
| Key Vault | Key Vault Secrets User（只用于将来可能接入的第三方密钥） |

- 在仓库里开启 GitHub 秘密扫描和推送保护；本地开发使用 `az login` 的开发者身份（DefaultAzureCredential）。
- 成本护栏：给资源组设 50 美元预算告警；所有资源打上 `env` 和 `owner` 标签；比赛结束后执行 `azd down --purge`。

## 后果

- **正面**：评审期的环境可以随时重建；公开仓库里没有任何密钥；赛后清理只需一条命令。
- **负面**：Bicep 模板约占 A 半天时间。
- **风险**：RBAC 授权生效有几分钟延迟，部署后立刻冒烟测试可能失败。缓解办法是在部署后的钩子里先等待，再带重试执行冒烟测试。
